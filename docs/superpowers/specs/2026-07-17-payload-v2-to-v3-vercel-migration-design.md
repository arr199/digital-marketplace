# Payload v2 → v3 + Vercel Migration Design

## Goal

Migrate DigitalHippo from self-hosted Express + Payload CMS 2.x to Vercel hosting with Payload CMS 3.x, eliminating the Express server entirely.

## Why Payload 3.x

Payload CMS 2.x requires an Express server for its admin panel. Payload 3.x was rewritten as a native Next.js application — the admin panel renders as a React component inside the Next.js App Router, making it fully compatible with Vercel's serverless architecture.

---

## Section 1: Architecture Change

**What goes away:**
- The entire Express server layer (`src/server/server.ts`, `src/server/next-utils.ts`)
- Vercel runs Next.js directly with `next build` / `next start`
- Payload's admin panel goes from Express-mounted at `/sell` to a native Next.js route at `/sell`
- tRPC drops its Express middleware; the existing `src/app/api/trpc/[trpc]/route.ts` becomes the sole tRPC handler

**What Payload 3 gives us:**
- Admin panel renders as a React component inside the Next.js App Router
- REST API + Local API served directly from Next.js route handlers
- Auth via HTTP-only cookies, works naturally with Next.js
- Database adapter (MongoDB) is identical, no data migration needed

## Section 3: Config & Collection Changes

**`payload.config.ts`** moves to root:
- `buildConfig` imported from `payload` (not `payload/config`)
- `editor: lexicalEditor()` replaces `slateEditor()`
- Remove `bundler` — Payload 3 doesn't need it
- `serverURL` becomes optional (Vercel auto-detects)
- `routes.admin: '/sell'` keeps admin at existing path
- `sharp` added for image processing
- Type generation: `outputFile: path.resolve(__dirname, 'src/server/payload-types.ts')`

**Collections** — minimal API changes:
- Import `CollectionConfig` from `payload` instead of `payload/types`
- Import hooks from `payload` instead of `payload/dist/*`
- No rich text fields used in existing collections, so Lexical migration is config-only
- Upload config: add `sharp` to `payload.config.ts` instead of implicit v2 handling
- Access control and hooks — identical signatures, no logic changes needed

**`next.config.mjs`** (renamed for ESM):
```js
import { withPayload } from '@payloadcms/next/withPayload'

const nextConfig = { /* existing config */ }

export default withPayload(nextConfig)
```

## Section 4: tRPC Auth Migration

v2 auth middleware reads `req.user` from Express (set by Payload's Express middleware). In v3, there's no Express.

**Solution:** Use `payload.auth({ headers })` in the tRPC context.

**`src/trpc/trpc.ts`** changes:
- Context type changes from `ExpressContext` to `{ headers: Headers }`
- `isAuth` middleware calls `payload.auth({ headers })` to get current user
- `privateProcedure` works the same way

**`src/trpc/auth-router.ts`** — `loginUser` mutation:
- v2: `payload.login()` with Express `res` auto-sets the cookie
- v3 Local API: `payload.login()` returns `{ token, user, exp }`. Manually set `payload-token` cookie on response via Next.js `cookies().set()`

**`src/app/api/trpc/[trpc]/route.ts`:**
- `createContext` passes request headers so `isAuth` can call `payload.auth({ headers })`

## Section 5: Stripe Webhook

Move from `src/webhooks/stripeWebHook.ts` (Express-style) to `src/app/api/webhooks/stripe/route.ts` (Next.js Route Handler):

```ts
export async function POST(req: Request) {
  const body = await req.text()
  const signature = req.headers.get('stripe-signature') ?? ''
  // ... same logic, use payload.update() for order, nodemailer for receipt
  return Response.json({ received: true })
}
```

Payload 3's `withPayload` plugin handles raw body parsing internally.

---

## Section 6: Cart Route Protection

v2 uses Express middleware. v3 approach:
- **Client-side** (already works): Cart page `createSession` mutation redirects to `/sign-in` on auth error
- **Server-side**: Update `src/middleware.ts` to check `payload-token` cookie and redirect to `/sign-in?origin=cart` for `/cart` if unauthenticated
- Remove Express `cartRouter` and `payload.authenticate`

## Section 7: Build & Scripts

New `package.json` scripts:
```json
{
  "dev": "next dev",
  "build": "next build",
  "start": "next start",
  "generate:types": "payload generate:types",
  "lint": "next lint"
}
```

Vercel auto-detects Next.js and runs `next build`. The `withPayload` plugin ensures Payload compiles during build.

## Section 8: Environment Variables

Same variables, with these changes:

| Variable | Change |
|---|---|
| `NEXT_PUBLIC_SERVER_URL` | Set to Vercel deployment URL (e.g. `https://your-app.vercel.app`) |
| `PAYLOAD_CONFIG_PATH` | Remove — no longer needed |
| `PORT` | Remove — Vercel manages ports |
| `NEXT_BUILD` | Remove — no longer needed |
| `STRIPE_WEBHOOK_SECRET` | Update Stripe dashboard: `https://your-app.vercel.app/api/webhooks/stripe` |
| All others | Unchanged |
